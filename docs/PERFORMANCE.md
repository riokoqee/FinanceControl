# Оптимизация BeliLog 2.4

## 2.11 storage note (English)

Primary writes retry once after evicting the duplicate last-good copy on a quota error. A valid pre-replacement copy is best effort and adds storage only when available. The profile's browser estimate covers the entire site, including PWA caches; it is not a measurement of the separate localStorage limit. The historical performance measurements below are unchanged.

## Примечание к 2.11

При ошибке квоты основная запись повторяется один раз после удаления дополнительной рабочей копии. Снимок перед заменой сохраняется по возможности. Оценка в профиле относится ко всему сайту, включая PWA-кэш, и не измеряет отдельный лимит localStorage. Исторические замеры ниже не изменялись.

Замеры от 6 ноября 2026 года. База сравнения — `0467769` (2.3.0), результат — версия 2.4. Изменения сохраняют существующий формат данных и ключ `localStorage`; перенос журнала не нужен.

## Что изменено

- Обзор, трекер, профиль, список покупок и редакторы выделены в отдельные модули с загрузкой при открытии. Ошибка загрузки раздела оставляет доступными навигацию и локальные данные.
- В списке из 1000 товаров сначала отображаются 50 строк. «Показать ещё» добавляет следующие 50, сохраняя текущие поля, черновики и фокус. Новый товар сразу виден, даже если находится за пределами первых 50.
- Сводка месяца рассчитывается одним проходом. Сортировка, поисковый индекс, денежные и календарные форматтеры переиспользуются. Ввод поиска имеет приоритет перед обновлением таблицы; PDF использует актуальный запрос.
- Имя, email и бюджет сохраняются после 350 мс без ввода. Выход из формы, навигация и уход со страницы сохраняют корректный черновик сразу. Настройки темы, языка, валюты и аватара применяются сразу.
- Сохранение больше не выполняет несколько полных циклов валидации и копирования неизменённого журнала. Проверка актуальной версии перед записью, конфликты вкладок, защита повреждённых данных и дополнительная рабочая копия сохранены.
- Календарь и постер используют общий таймер смены дня и кеш расчёта серии. Счётчик награды анимируется отдельно от всего постера. Геометрия редактора аватара не измеряется заново при каждом движении указателя.
- Вариативный Manrope заменяет отдельные файлы каждой толщины; браузер выбирает нужные языковые поднаборы. Сокращены повторяющиеся пояснения в обзоре и профиле.
- `App.tsx` разделён на страницы, общие компоненты, расчёты и управление черновиком профиля. Доступность модальных окон проверяется и во время загрузки, и после повторного открытия.

## Результаты

Локальная production-сборка для GitHub Pages, Node 24.11, Chromium 156, окно 1280×900, английский язык, светлая тема, уменьшенное движение. WSL с 2 ГБ памяти, без искусственного замедления сети или процессора. Показаны отдельные локальные прогоны; для ввода профиля и поиска — медиана трёх действий.

| Сценарий | 2.3 | 2.4 |
| --- | ---: | ---: |
| 1000 товаров: отображаемые строки при открытии | 1000 | 50 |
| 1000 товаров: элементы DOM | 22 138 | 1245 |
| 1000 товаров: готовность списка | 6028 мс | 781 мс |
| 1000 товаров: отклик на ввод цены | 1044 мс | 116 мс |
| 50 000 расходов: готовность трекера | 2324 мс | 1570 мс |
| 50 000 расходов: поиск | 561 мс | 193 мс |
| 50 000 расходов: ввод символа имени | 4547 мс, включая сохранение | 78 мс, до отложенного сохранения |
| JS, запрошенный при открытии трекера, gzip | 122 КБ | 105 КБ |

Числа округлены. Размеры gzip получены сжатием реально запрошенных JS-файлов, без HTTP-заголовков. Это весь JS для готового трекера, включая его модули, а не только уменьшившийся входной файл. PDF и раньше загружался отдельно; его размер около 511 КБ gzip не входит в запуск. Вместо десяти Manrope-файлов в проверенных английских сценариях загружались один или два в зависимости от символов валют.

При 50 000 расходах отдельное сохранение профиля после выхода из поля заняло 2047 мс. Оно по-прежнему сериализует журнал и пишет основную и дополнительную копии; эта работа выполняется одним пакетом после ввода. Во время измеренного ввода до таймера не было обращений к хранилищу. Итоговое сохранённое имя проверено отдельно после сброса черновика.

Отложенная загрузка уменьшает стартовый объём, но первое открытие нового раздела требует его модулей: например, профиль без расходов открывался за 514 мс против 237 мс в исходном прогоне. Повторное открытие использует уже загруженный код. В предварительном прогоне новой версии список открывался за 620 мс, ввод цены занял 50 мс, а сохранение профиля на 50 000 расходах — 1209 мс. Точные времена зависят от устройства, памяти, сети и сборки мусора; уменьшение DOM, числа файлов шрифта и повторных операций хранения — более устойчивые показатели.

Для 50 000 расходов использован адаптер хранения строк в памяти, чтобы квота браузера не подменяла замер производительности ошибкой переполнения. JSON, валидация, объединение данных и интерфейс работают как обычно; стоимость записи браузером на диск не учитывается. Это нагрузочный сценарий, а не гарантия, что такой журнал поместится в `localStorage` на любом устройстве.

## Повторение замеров

```bash
npm ci
GITHUB_PAGES=true npm run build
npx playwright install chromium
GITHUB_PAGES=true npm run preview -- --port 5175 --strictPort
```

В другом терминале:

```bash
node scripts/performance.mjs
npx vitest bench src/lib/storage/storage.bench.ts --run
```

Браузерный скрипт создаёт отдельные контексты со своими данными и сохраняет `performance-results.json`. Можно задать `BELILOG_URL`, `BENCH_OUTPUT`, `BENCH_DIST` и `CHROMIUM_PATH`. Микрозамер Vitest отделяет стоимость валидации, объединения и сериализации от браузерного рендеринга; его времена нельзя напрямую сравнивать с таблицей выше.

## Проверки и дальнейшие шаги

Автоматические проверки включают расчёты, старые копии, PDF, кадрирование, серии, повреждения и переполнение хранилища, работу двух вкладок, сохранение при уходе, покупку без дублей, клавиатуру, мобильную вёрстку и контраст обеих тем на RU/EN. Новые браузерные регрессии фиксируют ограничение числа строк, сохранение фокуса при подгрузке, загрузку модулей по запросу и отложенное сохранение профиля.

Перед выпуском прошли `npm test` (282 проверки), `npm run build` и `npm run test:browser` (79 сценариев: 35 общих, 15 для хранения, 17 для подтверждения покупки и 12 для производительности). Проверка PDF во время незавершённого поиска скачивает настоящий файл и проверяет его содержимое по числу страниц.

Дополнительно проверены обе темы на экране 390 пикселей, постер со стриком, кадрирование и сохранение аватара после перезагрузки, а также скачивание настоящей PDF-копии и восстановление точных данных профиля, расходов с детализацией и списка покупок.

При дальнейшем росте журнала следующий существенный шаг — IndexedDB и сохранение изменённых записей отдельно вместо сериализации всей базы. Такая миграция потребует отдельного восстановления, проверки нескольких вкладок и совместимости PDF-копий; в этой версии формат хранения сохранён.
